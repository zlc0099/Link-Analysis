# Link-Analysis · Git 仓库接入体检 —— 需求与范围

> 版本：v0.1（设计草案）｜日期：2026-11-26｜状态：待评审
> 关联文档：[检查规则与评分](./02-rules-and-scoring.md) · [技术设计](./03-technical-design.md) · [开发计划](./04-development-plan.md)

## 1. 背景与目标

### 1.1 题目要求对照

| # | 题目要求 | 本项目的落点 |
|---|---|---|
| 1 | Web 页面输入公开 Git 仓库链接（至少 GitHub） | 纯前端 SPA，支持 GitHub 仓库 URL、`git@` 形式与 `owner/repo` 简写 |
| 2 | 识别 README、依赖清单、启动脚本完整度 | 「文档 / 依赖 / 启动」三个维度、可解释计分 |
| 3 | 识别 Windows 专用脚本 | `.bat / .cmd / .ps1 / .vbs` 清单（信息项，不直接扣分） |
| 4 | 识别硬编码路径 | 盘符路径、`/Users/`、`/home/`、`file://`、UNC |
| 5 | 识别密钥与敏感信息风险 | 私钥、`.env` 入库、高置信 Key、Bearer、凭证文件，证据脱敏 |
| 6 | 可视化展示 + 接入就绪度评分 + 主要风险清单 | 报告页、五维评分、P0–P3 风险清单 |
| 7 | 加分：AI 评分/接入建议 | 本版不做，预留接口（见 §2.3） |
| 8 | 交付 GitHub 仓库、AI_USAGE.md、更新跟踪设计 | 见 §6 验收清单 |

### 1.2 产品定位

输入一个公开 GitHub 仓库链接，在浏览器内完成静态体检，1 分钟内输出「新人能否顺利接手、坑在哪」的可解释报告。

### 1.3 目标用户

| 用户 | 场景 | 最关心 |
|---|---|---|
| 接手仓库的开发者 | 拿到外包/前同事的仓库，准备本地跑起来 | 文档够不够、依赖锁没锁、路径是否绑定个人环境 |
| 技术负责人 / 验收人 | 供应商交付代码验收 | 是否有密钥泄漏、接入成本、风险优先级 |
| 面试 / 评审者 | 打开在线演示，粘贴一个公开仓库 | 核心链路真实可用、结果可信、不造假 |

### 1.4 成功标准

- 核心链路真实可跑：输入真实公开仓库 → 完整报告，不依赖预制数据
- 评分可解释：每个失分项可回溯规则 ID 与证据
- 报告可交付：可导出 Markdown，带 commit、分析时间、覆盖率
- 交付完整：公开 GitHub 仓库 + 在线演示 + README + `AI_USAGE.md` + 更新跟踪设计
- 诚实：不夸大扫描能力，不展示完整密钥，不伪造指标

## 2. 范围

### 2.1 P0 必须交付

**输入与拉取**

- 支持 `https://github.com/{owner}/{repo}`（含 `.git`、尾部斜杠）、`git@github.com:{owner}/{repo}.git`、`owner/repo` 简写
- 拒绝非 GitHub 域名并说明原因；仓库不存在 / 私有 / 空仓库有明确提示
- 自动使用默认分支；读取仓库元信息与 HEAD commit SHA；递归文件树
- 可选 GitHub Token（仅存 localStorage，仅用于 `api.github.com`）提升额度

**分析（四类）**

- 文档：README 存在性、安装/构建说明、配置说明、结构质量
- 依赖：依赖清单、锁文件/固定版本、清单可解析
- 启动：启动线索、README 启动命令、运行时版本声明、跨平台启动
- 跨平台：盘符路径、`/Users/`、`/home/`、`file://`、UNC；Windows 脚本清单（信息项）
- 安全：私钥、真实 `.env` 入库、高置信 Key、Bearer/凭证文件/通用敏感赋值，全程脱敏

**报告**

- 0–100 接入就绪度评分（五维等权、分项计件），P0 红线封顶 39
- 等级 A/B/C/D + 结论 + 覆盖率提示
- 主要风险清单（P0/P1 置顶），证据定位到文件:行，链接固定到 commit
- 评分明细（每条分项的通过 / 失败 / 不适用与证据）
- 加载进度、取消、空仓库、404、限流、Tree 截断、部分文件失败等状态
- 导出 Markdown（含 `owner/repo @ branch @ sha`、分析时间、覆盖率、脱敏证据）

**交付**

- GitHub Pages 在线演示（URL 写入 README）
- README：产品说明、快速开始、规则与评分口径、更新跟踪四问设计、验证记录、限制
- `AI_USAGE.md`：工具清单、验证方法、至少 1 条真实 AI 纠错记录
- 真实仓库验证记录（3 个公开仓库，记录 commit 与结果摘要）
- 演示仓库（用假值 `.env` 展示红线，需用户确认后创建）

### 2.2 P1 可延后（时间富余再做）

- 报告本地缓存与「最近体检」列表（IndexedDB）
- 复检按钮：比较 HEAD SHA，提示 commit 是否变化
- 按 blob SHA 的增量重扫（设计已完成，见技术设计 §9）
- 报告分享链接（`?repo=owner/name` 自动分析）
- Windows 脚本作用猜测细化（install/start/build/test）
- 历史报告差异视图（新增 / 消除风险）

### 2.3 不做（本期明确排除）

- GitLab/Gitee/Gitea 等非 GitHub 源（预留 Provider 扩展点）
- 私有仓库 OAuth 登录
- 真实 clone / 安装 / 构建 / 运行验证（只做静态体检）
- AI 评分/建议（接口预留，UI 不出现未完成入口）
- 账号体系、服务端存储、数据库
- CLI、浏览器插件、GitHub App
- 指定 tag/commit 的分析（含 `/tree/` 的链接按默认分支分析并提示）
- 依赖漏洞扫描（CVE）、许可证合规、代码质量审查

## 3. 用户与故事

### 3.1 角色

| 角色 | 类型 | 职责 |
|---|---|---|
| 使用者（开发者 / 验收人） | 人 | 输入链接、阅读报告、导出整改清单 |
| GitHub REST API | 外部数据源 | 仓库元信息、commit、文件树、文件内容 |
| Link-Analysis | 浏览器内工具 | 拉取、规则分析、评分、可视化；不保存到服务器 |

无管理员、无审核人、无系统账号。

### 3.2 主故事

> 李工准备接手外包团队交付的 `acme/legacy-portal`。粘贴链接后，报告显示：README 有安装说明但无启动命令，`package.json` 无锁文件，源码里有一处 `/Users/li/...` 路径，未发现密钥。评分 **76 / B「小修后接入」**。他导出 Markdown，把「补锁文件、补启动命令、改相对路径」三条发给对方。

评分口径见 [规则与评分 §4](./02-rules-and-scoring.md)：文档 16 + 依赖 14 + 启动 11 + 跨平台 15 + 安全 20 = 76。

### 3.3 红线故事

> 另一个仓库检出 `.env` 已提交且含非占位值：原始分 56，触发 P0 红线，总分封顶 **39 / D**，结论「先轮换密钥并清理 Git 历史，再谈接入」。报告只展示变量名与脱敏值，不复制完整密钥。

### 3.4 端到端流程

1. 首页输入链接 → 就地校验并解析 owner/repo
2. 拉取仓库元信息 → 默认分支 → HEAD commit SHA → 文件树（递归）
3. 按优先级筛选候选文件（≤400 个、单文件 ≤512KB）
4. 并发拉取文件内容（raw CDN，不计 API 额度）
5. 规则引擎逐文件 / 全树分析 → findings（含证据、脱敏、置信度）
6. 评分聚合 → 五维得分 → P0 封顶 → 等级与结论
7. 报告页渲染 → 导出 Markdown / 复检（P1）/ 回到首页
8. 全程可取消；任何阶段失败给出可行动的错误提示

### 3.5 反向推演（防断链）

| 从结果倒推 | 检查 | 结论 |
|---|---|---|
| 导出的报告 | 是否带 commit、时间、覆盖率？ | 必须带，否则无法判断时效 |
| 证据链接 | 文件变动后是否失效？ | 链接固定到 commit SHA，行号随快照 |
| 第二次体检 | 如何知道仓库变了？ | 比较 HEAD SHA，报告标注新旧 commit（P1） |
| 限流兜底 | 旧报告会不会被误认为最新？ | 旧报告明确标「已过期 / 基于旧 commit」 |
| 密钥证据 | 会不会二次扩散泄漏？ | 全程脱敏，不提供复制完整值入口 |

- URL 输入（回车提交）+ 就地错误提示

### 4.2 加载

- 阶段进度：解析链接 → 读取仓库 → 获取文件树 → 拉取文件（x/y）→ 分析 → 生成报告
- 可取消；失败显示阶段与原因

```text

[覆盖率 / 限流 / 部分失败 横幅]

硬编码路径明细（源码计分，文档仅提示）
密钥与敏感信息（脱敏）
评分明细（每条规则的通过 / 失败 / 不适用）

```

### 4.4 状态清单

| 状态 | 触发 | 用户看到 |
|---|---|---|
| idle | 初始 | 输入表单 + 示例 |
| validating | 提交 | 链接格式错误提示（不发请求） |
| loading | 拉取中 | 阶段进度、API 额度提示、取消按钮 |
| done | 成功 | 完整报告 + 覆盖率 |
| partial | 部分文件失败 / 树截断 | 报告 + 醒目「数据不完整」横幅 |
| error | 404 / 网络 / 空仓库 / 限流 | 原因 + 建议动作 + 重试 |
| cancelled | 用户取消 | 回到首页，保留输入 |

### 4.5 视觉方向

- 中文优先、极简文案；「体检报告」气质：细线、等宽数字、克制的青绿强调色
- 浅色冷调；避免大面积模糊 / 渐变背景动画（性能与还原度考虑）
- 响应式检查 1440 / 768 两档；Chrome/Edge 最新版为主
- 图表用手写 SVG/CSS（分数环、维度条），不引入图表库

## 6. 验收清单

1. 链接：`.git` / `git@` / 尾部斜杠 / 简写均可用；非 GitHub、私有、空仓库有正确提示
2. 报告：中等仓库（<300 文件）60 秒内出完整报告；阶段进度可见；可取消
3. 四类检查：每类都有证据（文件:行 + commit 固定链接），密钥全程脱敏
4. 评分：每个失分项可展开到规则 ID；P0 封顶 39 生效；等级与结论符合口径
5. 覆盖率：Tree 截断 / 文件失败时显示「数据不完整」，不伪造满分
6. 导出：Markdown 含 repo / branch / sha / 分析时间 / 覆盖率 / 脱敏证据
7. 单元测试：全部规则 ID 至少 1 正例 + 1 反例；评分边界（100 / 76 / P0 封顶）通过
8. 真实仓库：3 个公开仓库验证，记录 commit 与结果摘要；人工抽查 5 条证据
9. 页面：1440 / 768 无横向滚动；加载 / 错误 / 限流 / 截断态可用；控制台无报错
10. 部署：GitHub Pages 在线可用；README 链接可访问
11. 文档：README 更新跟踪四问齐全；`AI_USAGE.md` 含真实 AI 纠错记录与验证方法
12. 安全与卫生：仓库无真实密钥；截图 / 导出不出现完整密钥；Token 不写入日志或 URL
13. 自检：用本工具分析 Link-Analysis 自身，结果与预期一致并记录
14. 诚实：未实现的能力（AI、增量对比）明确标注为「设计」或「未实现」

## 8. 假设与限制

- 仅分析公开 GitHub 仓库；默认分支；静态扫描，不执行代码、不安装依赖
- 匿名 API 60 次/小时/IP；带 Token 5000 次/小时
- 扫描上限 400 文件、单文件 512KB；超大仓库覆盖率会下降并明确提示
- 密钥检测基于模式与启发式，不保证穷尽；示例 / 占位符会被过滤
- 首版不分析私有仓库、子模块内容、Git 历史（只扫当前快照）
- 48 小时交付，优先保证核心链路与可解释性

## 9. 术语

| 术语 | 含义 |
|---|---|
| manifest | 依赖清单，如 `package.json`、`requirements.txt`、`pom.xml` |
| lockfile | 锁定依赖版本的锁文件，如 `package-lock.json`、`poetry.lock` |
| 覆盖率 | 成功分析的文件数 / 应分析候选文件数；截断或失败会导致不足 |
| P0 红线 | 私钥、真实 `.env` 入库、高置信 Key，命中即总分封顶 39 |
| 脱敏 | 仅展示密钥前 4 位与后 2 位，中间以 `****` 代替 |
| 信息项 | 展示但不参与评分，如 Windows 专用脚本清单 |
| 增量重扫 | 基于 blob SHA 缓存只重扫变更文件（设计，P1） |
